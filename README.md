# hopecore

Персональный трекер вакансий. Локальный однопользовательский инструмент: хранит вакансии, добавленные вручную по ссылке, статус прохождения по каждой и умеет проверять, не снята ли вакансия с публикации.

Работает офлайн на машине кандидата, без облачных зависимостей. В сеть выходит только когда вы сами нажимаете «Опросить».

## Что уже работает

Этап 1 (MVP) готов целиком:

- Добавление вакансии по ссылке и правка карточки вручную: должность, компания, грейд, технологии, зарплатная вилка, формат работы, дата открытия.
- Таблица вакансий с сортировкой по любому столбцу; неактивные скрыты по умолчанию.
- Карточка вакансии со статусом кандидата: отклик, этап собеседования, контакт HR, зарплаты, сопроводительное письмо.
- Проверка активности по кнопке — одной вакансии или всех сразу. Ручное решение об активности сильнее результата проверки: расхождение показывается, но не исправляется само.

Этап 2 (заполнение карточки через языковую модель) в работе: настроены провайдеры и выбор модели, дальше идут скачивание страницы, извлечение полей и предпросмотр. Поиск вакансий по критериям через API источников отложен до Этапа 2.1 — `api.hh.ru` больше не отдаёт вакансии анонимно.

Этап 3 не начат: нейроблок и приём резюме собеседований. В карточке на их месте стоят заглушки.

Подробный статус по задачам — в [`docs/poject/README.md`](docs/poject/README.md).

## Стек

| Слой | Технологии |
|---|---|
| Backend | Go 1.22, stdlib `net/http`, gorm 1.25 + `glebarez/sqlite` (без CGO) |
| БД | SQLite, файл рядом с приложением |
| Frontend | React 18 + Vite, Tailwind 4, TanStack Query и Table v9, компоненты в стиле shadcn/ui |
| Языковые модели | Gemini, Claude, DeepSeek — по ключам в окружении, выбор перед каждым запуском |
| Запуск | Docker Compose: `backend` (Go) и `frontend` (nginx со статикой) |

## Запуск

Нужен только Docker с Compose.

```bash
git clone https://github.com/Hundsamurai/hopecore.git
cd hopecore
docker compose up --build
```

Откройте `http://127.0.0.1:8080`.

Остановить — `docker compose down`. База остаётся в каталоге `data/` и переживает пересборку.

Файл базы можно открывать с хоста для просмотра (`sqlite3 data/hopecore.db`), но **не пишите в него, пока приложение работает**: приложение и ваша сессия `sqlite3` окажутся двумя писателями по разные стороны bind-mount. Для правок используйте API или сначала остановите контейнеры. Резервная копия — обычное копирование файла при остановленном приложении.

### Настройка

Файл `.env` не обязателен: без него берутся значения по умолчанию. Если нужно что-то поменять:

```bash
cp .env.example .env
```

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `HOST_PORT` | порт на хосте, где открывается админка | `8080` |
| `DATA_DIR` | каталог с файлом SQLite | `./data` |
| `CHECK_TIMEOUT` | таймаут одного запроса к сайту вакансии | `10s` |
| `CHECK_CONCURRENCY` | сколько ссылок опрашивать параллельно | `4` |
| `LOG_LEVEL` | `debug`, `info`, `warn` или `error` | `info` |

Логи — `docker compose logs -f backend`.

### Языковые модели

Чтобы включить заполнение карточки моделью, положите в `.env` хотя бы один ключ:

```bash
GEMINI_API_KEY=...
# ANTHROPIC_API_KEY=...
# DEEPSEEK_API_KEY=...
```

Без ключей приложение работает как обычно, только кнопка заполнения выключена. Провайдер и модель выбираются вручную перед каждым запуском: ничего не запускается по расписанию, все траты по квоте инициируете вы. Ключи не попадают ни в логи, ни в ответы API.

Полный список переменных — `LLM_*` в [`.env.example`](.env.example) и в [`docs/poject/structure.md`](docs/poject/structure.md).

## Безопасность

**У приложения нет авторизации** — так решено в ТЗ, это личный инструмент. Поэтому порт публикуется только на `127.0.0.1` и снаружи машины трекер недоступен. Если менять проброс порта на `0.0.0.0` или выставлять сервис в сеть, авторизацию придётся добавить: сейчас любой, кто дотянется до порта, получит полный доступ к данным.

## Разработка

Backend:

```bash
cd backend
go test ./...                      # тесты: unit + интеграционные поверх in-memory SQLite
DB_PATH=./hopecore.db go run ./cmd/server
```

Frontend (ожидает backend на `localhost:8080`, прокси настроен в `vite.config.ts`):

```bash
cd frontend
npm install
npm run dev                        # http://localhost:5173
npm run build                      # проверка типов + прод-сборка
npm run smoke                      # рендер экранов в строку: ловит битые импорты
```

Автоматических тестов на фронте нет по решению при проектировании — интерфейс проверяется руками, а `npm run smoke` страхует от несобираемого состояния.

## API

Базовый префикс `/api`, формат JSON, авторизации нет.

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/health` | проверка живости |
| `GET` | `/vacancies` | список; `include_inactive`, `sort`, `order` |
| `POST` | `/vacancies` | добавить (обязателен `url`) |
| `GET` | `/vacancies/{id}` | карточка вместе со статусом кандидата |
| `PATCH` | `/vacancies/{id}` | частичная правка; `null` очищает поле |
| `DELETE` | `/vacancies/{id}` | удалить вместе со связанными записями |
| `PUT` | `/vacancies/{id}/activity` | ручной статус: `true`, `false` или `null` для возврата к авто-проверке |
| `POST` | `/vacancies/{id}/check` | опросить одну вакансию |
| `POST` | `/vacancies/check` | опросить все, вернуть сводку |
| `GET` | `/vacancies/{id}/candidate-status` | статус кандидата |
| `PUT` | `/vacancies/{id}/candidate-status` | сохранить статус (заменяет представление целиком) |
| `GET` | `/llm/providers` | доступные провайдеры моделей и их модели |

Ошибки приходят в едином виде:

```json
{ "error": { "code": "validation_failed", "message": "...", "fields": { "url": "..." } } }
```

Параметры, правила валидации и примеры — в [`docs/poject/api.md`](docs/poject/api.md).

Пример: добавить вакансию и сразу проверить, жива ли она.

```bash
curl -X POST http://127.0.0.1:8080/api/vacancies \
  -H 'Content-Type: application/json' \
  -d '{"url":"https://hh.ru/vacancy/123","company":"HH","grade":"senior","tech_tags":["go"]}'

curl -X POST http://127.0.0.1:8080/api/vacancies/1/check
```

## Как работает проверка активности

Трекер запрашивает страницу вакансии и смотрит на код ответа: `2xx` — вакансия на месте, `404` или `410` — снята, всё остальное (`403`, `429`, `5xx`, таймаут, недоступный хост) считается «непонятно» и прежнее значение не меняет.

Результат проверки и ваше решение хранятся отдельно. Если вы вручную пометили вакансию активной или снятой, проверка это не переопределит — только покажет расхождение иконкой в таблице. Вернуть автоматический режим можно переключателем «По проверке» в карточке.

Крона нет: ни один запрос к чужим сайтам не уходит без вашего нажатия.
