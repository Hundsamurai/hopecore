# Справочник API

Базовый префикс `/api`. Формат — JSON в UTF-8. Авторизации нет: сервис слушает только `127.0.0.1`.

В проде запросы идут через nginx, который проксирует `/api` на backend, поэтому фронт обращается по относительному пути и CORS не нужен.

## Общие соглашения

**Неизвестные поля в теле запроса отвергаются.** Опечатка в имени поля должна быть заметна сразу, а не молча игнорироваться, поэтому лишнее поле даёт `400 invalid_json`.

**`PATCH` различает три состояния поля.** Поле отсутствует — не трогать; `null` — очистить; значение — записать. Это единственный способ отличить «оставь как было» от «сотри».

**`PUT` заменяет представление целиком.** Отсутствующее поле означает пустое значение. Так работает `candidate-status`: форма в интерфейсе всё равно присылает всё своё состояние.

**Списки завёрнуты в объект** — `{"items": [...]}`, а не голый массив: так позже можно добавить метаданные, не ломая клиента.

**Некорректный `{id}`** (не число, ноль, отрицательный) даёт `404`, а не `400`: для клиента это просто несуществующий адрес.

**Ограничение размера тела** — 1 МиБ.

**Даты** приходят и принимаются строкой `YYYY-MM-DD`. Метки времени — RFC 3339 в UTC.

## Ошибки

Единый формат для всех ошибок, включая служебные 404 и 405 от роутера:

```json
{
  "error": {
    "code": "validation_failed",
    "message": "некорректные данные запроса",
    "fields": { "url": "ожидается ссылка со схемой http или https" }
  }
}
```

| Код | HTTP | Когда |
|---|---|---|
| `validation_failed` | 400 | данные не прошли проверку; в `fields` — сообщения по полям |
| `invalid_json` | 400 | тело не разобралось, неизвестное поле, неверный тип, больше одного объекта |
| `not_found` | 404 | записи нет либо адрес не существует |
| `method_not_allowed` | 405 | путь есть, метод не тот; заголовок `Allow` сохраняется |
| `internal_error` | 500 | внутренняя ошибка; подробности уходят в лог, не клиенту |

Имена ключей в `fields` совпадают с именами полей формы, поэтому маппинг на инпуты прямой.

## Вакансии

### Объект вакансии

```json
{
  "id": 1,
  "url": "https://hh.ru/vacancy/777",
  "title": "Go-разработчик",
  "company": "HH",
  "grade": "senior",
  "tech_tags": ["go", "postgres"],
  "opened_date": "2026-08-01",

  "salary_from": 300000,
  "salary_to": 450000,
  "salary_currency": "RUB",
  "salary_gross": true,
  "work_format": "remote",

  "is_active": true,
  "activity_conflict": false,
  "auto_is_active": true,
  "manual_is_active": null,
  "last_checked_at": "2026-08-10T12:00:00Z",
  "last_check_code": 200,
  "last_check_error": "",

  "created_at": "2026-08-01T10:00:00Z",
  "updated_at": "2026-08-10T12:00:00Z",
  "candidate_status": null
}
```

Про поля активности:

| Поле | Смысл |
|---|---|
| `is_active` | вычисленное значение для отображения: `manual ?? auto ?? true` |
| `auto_is_active` | результат последней проверки; `null` — определить не удалось |
| `manual_is_active` | решение пользователя; `null` — override не задан |
| `activity_conflict` | `true`, когда решение пользователя расходится с результатом проверки |

Зарплатные поля — это **вилка из объявления**. То, что предложили лично кандидату, живёт в `candidate_status.offered_salary`.

### `GET /api/vacancies`

| Параметр | Значения | По умолчанию |
|---|---|---|
| `include_inactive` | `true`, `false` | `false` — неактивные скрыты |
| `sort` | `updated_at`, `created_at`, `company`, `opened_date`, `grade` | `updated_at` |
| `order` | `asc`, `desc` | `desc` |

Фильтр активности в SQL — `COALESCE(manual_is_active, auto_is_active, 1) = 1`, то есть то же правило, что и в `is_active`. Порядок дополняется сортировкой по `id`, чтобы выдача была стабильной при равных значениях.

Интерфейс запрашивает список целиком и сортирует на клиенте: это позволяет сортировать по столбцам, которых нет в белом списке сервера (этап собеседования, вилка, дата отклика).

```json
{ "items": [ { "id": 1, "...": "..." } ] }
```

### `POST /api/vacancies`

Обязателен только `url`. Ответ — `201` с созданной вакансией.

```bash
curl -X POST http://127.0.0.1:8080/api/vacancies \
  -H 'Content-Type: application/json' \
  -d '{"url":"https://hh.ru/vacancy/777","title":"Go-разработчик","company":"HH",
       "grade":"senior","tech_tags":["go"],"salary_from":300000,"salary_to":450000,
       "salary_currency":"rub","salary_gross":true,"work_format":"remote"}'
```

Правила проверки:

| Поле | Правило |
|---|---|
| `url` | обязательно, схема `http` или `https`, непустой домен |
| `title`, `company` | до 2000 символов |
| `grade` | из набора грейдов либо пусто |
| `work_format` | из набора форматов либо пусто |
| `tech_tags` | до 50 тегов по 100 символов; пробелы обрезаются, пустые отбрасываются, порядок сохраняется |
| `opened_date` | `YYYY-MM-DD` или `null` |
| `salary_from`, `salary_to` | ≥ 0, ≤ 10⁹, и `from ≤ to`, если заданы обе |
| `salary_currency` | три латинские буквы, приводится к верхнему регистру |

Нормализация зарплатных полей:

- вилка задана, валюта пуста → подставляется `RUB`;
- вилки нет → `salary_currency` и `salary_gross` очищаются, потому что без вилки ничего не означают;
- односторонняя вилка допустима: «от 300 000» и «до 500 000» равно осмысленны.

### `GET /api/vacancies/{id}`

Вакансия вместе с вложенным `candidate_status` — карточка получает всё одним запросом. `404`, если записи нет.

### `PATCH /api/vacancies/{id}`

Частичное обновление. `null` очищает поле, кроме `url` — ссылку очистить нельзя, вакансия без неё бессмысленна.

```bash
# сменить грейд, очистить компанию и вилку
curl -X PATCH http://127.0.0.1:8080/api/vacancies/1 \
  -H 'Content-Type: application/json' \
  -d '{"grade":"middle","company":null,"salary_from":null,"salary_to":null}'
```

Согласованность вилки проверяется на итоговых значениях, а не на теле запроса: если в базе `salary_from = 400000`, а в `PATCH` пришло `salary_to = 100000`, запрос будет отклонён.

### `DELETE /api/vacancies/{id}`

`204` без тела. Статус кандидата, резюме собеседований и нейроблок удаляются каскадом на уровне БД. Повторное удаление — `404`.

## Активность вакансии

Проверка запускается только вручную. HTTP-код трактуется так:

| Ответ сайта | Вывод |
|---|---|
| 2xx | вакансия на месте |
| 404, 410 | вакансия снята |
| 401, 403, 429, 5xx, превышен лимит редиректов | неизвестно, прежнее значение сохраняется |
| таймаут, ошибка DNS, отказ соединения | неизвестно, `last_check_code` остаётся пустым |

### `PUT /api/vacancies/{id}/activity`

Ручной статус. Поле обязательно присутствовать; `null` снимает override и возвращает вакансию к результату проверки.

```json
{ "manual_is_active": true }
```

Ответ — обновлённая вакансия. Это действие обновляет `updated_at`, поэтому вакансия поднимается в списке.

### `POST /api/vacancies/{id}/check`

Опрашивает одну вакансию, тело не нужно. Ответ — обновлённая вакансия.

Проверка выполняется даже при заданном override: пользователь нажал кнопку осознанно и вправе увидеть, что говорит сайт. Override при этом не меняется, расхождение отражается в `activity_conflict`.

### `POST /api/vacancies/check`

Опрашивает все вакансии, кроме помеченных вручную как неактивные. Параллельность — `CHECK_CONCURRENCY`. Ответ:

```json
{ "checked": 4, "skipped": 1, "became_inactive": 1, "unknown": 1, "failed": 1 }
```

| Поле | Смысл |
|---|---|
| `checked` | сколько вакансий реально опросили |
| `skipped` | сколько пропустили как закрытые вручную |
| `became_inactive` | сколько перешло из активных в снятые |
| `unknown` | сайт ответил, но код неинформативен |
| `failed` | ответа не было вовсе |

Проверка активности **не** обновляет `updated_at`: иначе массовый прогон перетасовал бы таблицу, отсортированную по дате изменения, хотя пользователь ничего не менял.

Прогон ограничен 4 минутами. При обрыве уже сохранённые результаты остаются в БД, а клиент получает сводку по успевшим проверкам.

## Статус кандидата

Связь с вакансией строго 1:1.

```json
{
  "id": 1,
  "vacancy_id": 1,
  "cover_letter": "Здравствуйте, откликаюсь…",
  "sent_at": "2026-08-05",
  "interview_stage": "техническое интервью",
  "hr_contact": "@hr_example",
  "interview_record_url": "",
  "offer_received": false,
  "offered_salary": 350000,
  "real_salary": null,
  "market_salary_data": "медиана 300k",
  "created_at": "2026-08-05T10:00:00Z",
  "updated_at": "2026-08-05T10:00:00Z"
}
```

### `GET /api/vacancies/{id}/candidate-status`

Статус отдельным запросом. `404` с пояснением, если ещё не заполнен.

### `PUT /api/vacancies/{id}/candidate-status`

Upsert: первый вызов создаёт запись, последующие обновляют её, `id` и `created_at` сохраняются. Заменяет представление целиком — не присланное поле обнуляется.

Проверки: `interview_record_url` должен быть ссылкой, если непустой; зарплаты неотрицательны и не больше 10⁹; `cover_letter` до 20 000 символов, остальные текстовые поля до 2000.

Этап собеседования — свободный текст: в ТЗ набор этапов не зафиксирован, а у каждой компании он свой.

Сохранение статуса обновляет `updated_at` вакансии: для пользователя это правка карточки, и вакансия должна подняться в списке.

## Языковые модели

### `GET /api/llm/providers`

Провайдеры, которыми можно пользоваться: те, у которых задан ключ и есть хотя бы одна модель.

```json
{
  "items": [
    {
      "id": "gemini",
      "label": "Gemini",
      "models": ["gemini-2.5-flash", "gemini-2.5-pro"],
      "default_model": "gemini-2.5-flash",
      "price_known": false
    }
  ]
}
```

| Поле | Смысл |
|---|---|
| `models` | список разрешённых моделей; клиент не может подставить произвольную |
| `default_model` | первая из списка, предвыбирается в интерфейсе |
| `price_known` | задана ли цена в конфигурации; если нет, показываются только токены без суммы |

Пустой список — не ошибка, а рабочее состояние: ключей нет, заполнение через модель недоступно, всё остальное работает.

**Ключи наружу не отдаются** ни в каком виде и не пишутся в логи. Это закреплено тестом.

### Планируется на Этапе 2

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/api/vacancies/{id}/extract` | извлечь поля со страницы; в вакансию не пишет, возвращает найденное для предпросмотра |
| `GET` | `/api/llm/runs` | журнал запусков: провайдер, модель, токены, оценка стоимости, статус |
| `GET` | `/api/llm/runs/{id}` | запуск целиком, включая сырой ответ модели |

## Справочные значения

**Грейды** (`grade`): `intern`, `junior`, `middle`, `senior`, `lead`. Пустая строка допустима — вакансию можно добавить до того, как уровень понятен.

**Форматы работы** (`work_format`): `onsite`, `hybrid`, `remote`. Пустая строка допустима.

Оба набора зафиксированы в `internal/model`, чтобы валидация в API и подсказки в интерфейсе брались из одного места.
